# Native DREAM GPU training — self-hosted and resumable

This training profile uses the same pinned CUDA/PyTorch image as the native inference worker. It runs on an NVIDIA machine that we control. It does not launch a hosted notebook or download an outside foundation model.

## One-time local folders

On the GPU host, create the private data directory and training controls:

```sh
mkdir -p dream-host/native-training-data dream-host/training-state
cp dream-host/native-training.env.example dream-host/native-training.env
```

Keep the reviewed dataset files under `dream-host/native-training-data/`. Required inputs:

- `approved-records.jsonl`: native pretraining records that each have verified source/license metadata, rights, privacy, quality and explicit training approval.
- `sft-train.jsonl` and `sft-validation.jsonl`: separate, human-reviewed instruction examples with no overlap by source group or content.
- `sft-audit-gate.json`: the current hash-bound privacy and review gate generated by DREAM's existing SFT audit workflow.

Do not train on private user conversations, learner records, passwords, scraped personal data, unreviewed web pages, or model-generated feedback loops. A consented contribution is still subject to human review. The repository's `data/README.md` defines the acceptance rules and license screen.

## Run / resume training

```sh
bash scripts/train-native-dream-gpu.sh
```

The trainer:
1. Confirms that CUDA is available inside the container.
2. Audits the approved corpus and prepares deterministic source-group-isolated train/validation/test splits.
3. Trains the native DREAM transformer, saving atomic resumable checkpoints and optimizer/RNG state every 100 steps.
4. Runs native SFT only against the supplied, separately reviewed dataset and hash-bound audit gate.
5. Audits the final checkpoint, evaluates it against the held-out pretraining test split and runs the technical release consistency gate.

Persistent checkpoints and reports are stored on the host under `dream-host/training-state/`, not in the container filesystem. Run the command again to resume from the saved checkpoint. A resumed run must use the same source data, manifest, architecture and audit inputs; the training scripts reject changed identities.

The first run performs 2,000 pretraining steps and 1,000 SFT steps. Later runs keep the pretraining checkpoint fixed by default and resume SFT with its saved optimizer state. Set `DREAM_NATIVE_CONTINUE_PRETRAINING=true` only when you deliberately want to continue base-model training; the pipeline then archives the old SFT checkpoint because its parent base has changed. Edit `dream-host/native-training.env` to change step counts or set a nonzero time budget. It is a manual, controlled training run—not a background process that consumes the GPU without limit.

## Review and publish

The trainer creates a candidate and reports in `dream-host/training-state/reports/`. Review the qualitative sample, language/task evaluations, corpus provenance and privacy/rights reports. The technical release gate checks checkpoint integrity and held-out metric consistency; it is not proof of useful model quality or legal approval.

After review, explicitly publish the candidate to the private R2 vault:

```sh
bash scripts/publish-native-dream-checkpoint.sh --approve-reviewed-candidate
```

The publisher rechecks the file hash against the release gate, uploads only to DREAM HOST's authenticated artifact API, and pins the returned hash in the local `dream-host/native-gpu.env`. It never exposes the raw R2 credentials.

Then set the encrypted Render environment variables on `dream-host-live` to:
- `DREAM_HOST_MODEL_NAME=dream-native-v1`
- `DREAM_HOST_ADAPTER_NAME=none`

Keep the current worker/client/artifact credentials distinct. After the HOST deploy is live, run `bash scripts/start-native-gpu-host.sh`. The worker fetches only the exact pinned checkpoint and joins the native DREAM chat queue.

## Persistence boundary

The host filesystem preserves training state across container rebuilds and restarts. It does not preserve data if the physical disk fails, nor does it create electricity or internet access. Back up `dream-host/training-state/` and the private input datasets to an independent protected storage location. The private R2 vault stores release artifacts, while the physical host performs training and inference.

The existing free Render HOST queue remains in-memory; this work does not silently claim pending chat jobs survive Render restarts. Durable queue migration is a separate change. The main DREAM AI application can keep its current managed inference fallback until native worker readiness is verified end-to-end.
